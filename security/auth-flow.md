# Auth Flow (Detailed)

**Status:** Active  
**Owner:** Backend Lead + Security Champion

Complementary to `architecture/sequence-flows.md` and `api-contracts/auth.md`. This file documents security details and state transitions.

## Phases

```
1. OTP request   → Supabase Edge → Twilio
2. OTP verify    → Supabase Edge issues Supabase JWT (5 min)
3. Exchange      → FastAPI maps phone → hr.employee, issues internal access (15 min) + refresh (30 days)
4. Refresh       → FastAPI rotates access + refresh
5. Logout        → FastAPI revokes refresh; mobile wipes secure storage + local DB
```

## Token shapes

### Supabase JWT (transient)
- Issuer: Supabase project.
- TTL: 5 min.
- Used only for `/v1/auth/exchange`.
- Never persisted to disk.

### Internal access JWT
- Issuer: FastAPI.
- Algorithm: RS256.
- TTL: 15 min.
- Claims: `iss`, `sub` (employee_id as string), `aud`, `exp`, `iat`, `jti`, `employee_id`, `device_id`.
- Stored in: `flutter_secure_storage` only. Never in SQLite, never in logs.

### Internal refresh JWT
- Issuer: FastAPI.
- Algorithm: RS256.
- TTL: 30 days.
- Claims: `iss`, `sub`, `aud=refresh`, `exp`, `iat`, `jti`, `device_id`, `session_id` (DB row).
- Rotated on every successful refresh. Old refresh becomes invalid.
- Stored in `sessions` table on backend (`refresh_jti`); used to detect re-use.

## Refresh re-use detection

If a refresh token is presented after it has been rotated (i.e. a stale token), the backend treats it as a compromise indicator:

1. Mark the entire `session` row as revoked.
2. Force re-login on the device.
3. Log a SEC event.

## Lockouts

| Trigger | Lockout |
|---|---|
| 5 wrong OTP codes for one phone | 5 min cooldown |
| 10 OTP requests per device per hour | 1 h cooldown |
| 3 detected refresh re-use events | session revoked + admin alert |

## Logout

- Mobile calls `POST /v1/auth/logout`. Server marks `sessions.revoked = TRUE` for that refresh.
- Mobile then:
  1. Clears `flutter_secure_storage` (access, refresh, device_id is **kept** for audit purposes; document in privacy notice).
  2. Wipes local SQLite tables (full DB delete, recreate empty).
  3. Routes to login screen.

## Session lifecycle

- Created on `/v1/auth/exchange`.
- Updated `last_seen_at` on each authenticated request.
- Auto-revoked after 30 days idle.
- Admin can revoke via Odoo backend (custom action on `field_mobile_sync.session`).

## Device binding

- `device_id` is generated by mobile at first launch (UUID v4) and stored in `flutter_secure_storage`.
- Sent as `X-Device-ID` header.
- Embedded in JWT.
- Used to detect token use from a different device.

## Force update

The exchange response carries `min_app_version`. If local app version is lower, mobile shows a blocking screen with link to the store. Hard requirement per NFR-100.

## Edge cases

| Case | Handling |
|---|---|
| Phone changes in Odoo | Old phone cannot log in; user must re-onboard with new phone |
| Employee deactivated mid-session | Next request → 401 `SESSION_EXPIRED` → forced logout |
| Device lost / stolen | Admin revokes session via Odoo |
| Clock skew on device | JWT includes `iat`; backend allows ±5 min drift |
| Multi-device | Multiple sessions per employee allowed; each has its own refresh |

## Auditable events

Every auth event lands in `audit_log`:

- `OTP_REQUESTED`, `OTP_VERIFIED`, `OTP_REJECTED`
- `SESSION_CREATED`, `SESSION_REFRESHED`, `SESSION_REVOKED`
- `REFRESH_REUSE_DETECTED`
- `EMPLOYEE_NOT_MAPPED`

PII is redacted in `audit_log` (last-4 phone digits, hashed device ID).
